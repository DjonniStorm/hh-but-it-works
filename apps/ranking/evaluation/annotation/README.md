# Human annotation batch: как размечать пары

Этот каталог — готовые к отправке экспертам батчи и инструкция по ним. Цель
пайплайна: получить независимые двойные человеческие метки
(`labelSource = human_double_annotation_v1`), без которых LTR не может быть
`productionApproved` (см. `evaluation/train_ltr.py --production-approved`).

Связанные доки: [`DATA_SOURCING.md`](../DATA_SOURCING.md) — откуда берутся
вакансии и какие данные законно использовать; [`data/README.md`](../data/README.md)
— карточка gold-набора.

## Батчи

| Батч                 | Датасет                      | Формат                           | Статус                                             |
| -------------------- | ---------------------------- | -------------------------------- | -------------------------------------------------- |
| `batch-001`          | `evaluation/data/gold.jsonl` | 168 пар: 21 need × 8 кандидатов  | LLM-судья разметил; human-разметка открыта         |
| llm-проход batch-001 | тот же                       | `evaluation/data/llm_gold.jsonl` | готов, `labelSource: llm_judge_v1` (не human gold) |

`batch-001` построен на controlled-synthetic gold: вакансии реальные
(«Работы России»), кандидаты вымышленные, сценарные метки эксперту не
показываются. Это первый калибровочный батч — он проверяет шкалу и сам
пайплайн. Продакшен-батч позже собирается из реального обезличенного пула по
[`DATA_SOURCING.md`](../DATA_SOURCING.md).

Файлы батча:

- `batch-001/pairs.csv` — blind-шаблон: одна строка = одна пара, меток нет;
- `batch-001/pairs.manifest.json` — sha256 датасета, число пар и полей. Если
  `gold.jsonl` меняется, манифест перестаёт сходиться — батч надо пересоздать
  командой экспорта ниже.

## Кто и что размечает

- Каждую пару оценивают **минимум два независимых аннотатора** (HR/рекрутер
  или доменный эксперт). Аннотаторы не советуются друг с другом.
- Разметчик заполняет в `pairs.csv` все строки под своим `annotator_id`
  (уникальное имя/псевдоним, например `hr-masha`; импорт отклоняет дубли).
- Каждый размечает **все** пары файла: импорт принимает только полное
  покрытие датасета.

### Колонки

| Колонка                   | Что заполнять                                                        |
| ------------------------- | -------------------------------------------------------------------- |
| `need_id`, `candidate_id` | не трогать — ключи пары                                              |
| `annotator_id`            | своё имя; adjudicator — `adjudicator:<имя>` (см. ниже)               |
| `qualification_label`     | 0..3 — квалификация (см. шкалу)                                      |
| `intent_label`            | 0..3 — мотивация/доступность кандидата                               |
| `overall_label`           | 0..3 — итоговая взаимная пригодность пары                            |
| `confidence`              | 0.5..1.0 — уверенность в own оценке; усредняется в sample weight     |
| `rationale`               | 1–2 фразы почему; **без PII** (телефоны, email, ФИО — импорт упадёт) |

### Шкала 0..3 (scaleVersion `labels-v1`)

Оценки независимые: `overall` — не среднее двух шкал, а собственное решение.

**qualification** — насколько кандидат соответствует требованиям вакансии:

- `0` — не соответствует: нет обязательных навыков/опыта, другая профессия;
- `1` — рядом с профессией: смежный опыт, критичные пробелы;
- `2` — почти подходит: основные требования закрыты, есть пробелы, которые
  можно доработать;
- `3` — полностью закрывает требования, включая обязательные.

**intent** — насколько кандидат реально готов к этому предложению:

- `0` — не ищет работу, не отвечает на связь;
- `1` — пассивен: смотрит редко, на прямые отклики не отвечает;
- `2` — открыт к предложениям: готов обсуждать, если вилка/условия сошлись;
- `3` — активно ищет: откликается, ведёт переписку, в процессе поиска.

**overall** — взаимная пригодность пары для найма:

- `0` — не выводить в подборку: жёсткий фильтр или заведомый отказ сторон;
- `1` — можно показать с оговорками: сомнительное соответствие или слабая
  мотивация;
- `2` — хороший кандидат: стоит звать на интервью;
- `3` — идеальная пара: проходит hard filter, почти наверняка доходим до
  оффера.

`confidence`: если шкала вызывает сомнение, а не оценка — такая пара обычно
расходится у аннотаторов и уходит в adjudication; confidence ниже 0.5 не
ставьте, лучше честно разойтись.

## Adjudication (конфликты)

- Любое расхождение по трём шкалам у пары — конфликт: его **не** усредняют.
- Конфликт решает третий эксперт с `annotator_id` вида `adjudicator:<имя>`,
  выставляя окончательные значения всех трёх шкал. Решение адjudикатора
  должно быть одно (несколько adjudicator-строк по паре обязаны совпадать).
- Adjudicator-строки добавляются **в тот же общий CSV** поверх строк
  аннотаторов (или в отдельный файл, который склеивается перед импортом).
- Если аннотаторы сошлись — adjudicator-строки к паре не нужны; импорт
  отклонит «лишнюю» adjudication согласованной пары.
- Импорт считает попарное согласие аннотаторов (по `overall`) и валит батч,
  если среднее согласие ниже `--min-agreement` (по умолчанию 0.6): слишком
  много споров = шкала непонятна, вернуться к гайду и переразметить.

## Импорт и следующие шаги

Из корня `apps/ranking`:

```bash
python evaluation/human_labels.py import \
  evaluation/data/gold.jsonl \
  <merged-annotations.csv> \
  evaluation/data/human/human_gold.jsonl
```

Импорт проверяет: полное покрытие пар, ≥2 аннотатора на пару, диапазон шкал
0..3, отсутствие PII, ≥2 кандидатов на need, adjudication-протокол,
`--min-agreement`. На выходе — JSONL в формате gold + отчёт
(`pairwiseOverallAgreement`, `adjudicatedPairs`, `labelHistogram`, число
аннотаторов). Затем:

1. закоммитить `human_gold.jsonl` (это и есть человеческий gold);
2. разбить по groups на train/calibration/test так, чтобы need не пересекались;
3. обучить: `python evaluation/train_ltr.py ... --production-approved`
   (флаг принимается только при `human_double_annotation_v1` и независимом
   human-calibration split);
4. прогнать held-out gate (`scripts/check_ml.sh`, `evaluation/benchmark.py`)
   и только после него менять артефакт в runtime.

## LLM-судья (сделано на batch-001)

Параллельно с human-разметкой batch-001 был проведен blind-проход LLM-судьи
(один аннотатор `llm-judge`, метки и scenario перед разметкой вырезаны):

```bash
python evaluation/human_labels.py import evaluation/data/gold.jsonl <annotations.csv> \
  evaluation/data/llm_gold.jsonl --label-source llm_judge_v1 --min-annotators 1
```

Результат: `evaluation/data/llm_gold.jsonl` + сплиты `llm_gold_*` (зеркалят
need-принадлежность `gold_*`), провенанс и сверка со сценариями —
`evaluation/data/llm_gold_provenance.json`. Итог честный: llm-порядок внутри
групп совпал со сценарным (mean Kendall tau 1.0) — такая разметка проверяет
пайплайн и порог шкалы, но не добавляет внешнего сигнала. Модель на llm-метках
учится и открывает замок только через `train_ltr.py --llm-approved`
(`approvalSource: llm_judge_v1`); human-путь (`--production-approved`) остаётся
отдельным и более строгим. Готовый бандл: `evaluation/artifacts/ltr-v1.5.0-llm/`
(с 2026-10-10 он же serving default образа; см. `evaluation/artifacts/README.md`).

## Экспорт нового батча

```bash
python evaluation/human_labels.py export <dataset.jsonl> <batch-dir>/pairs.csv
```

Команда пишет blind CSV и `pairs.manifest.json` (sha256 датасета, размеры
групп, шкалы). Батч из другого датасета размечается и импортируется так же —
путь к датасету передаётся в `import` явно.
