# Тестирование: сборка, защита и валидация

Движок — `packages/assessment-engine`. API держит попытку в Redis и пишет итог в `assessment_attempts`. Ответы и верные варианты на клиент не уходят.

## Как собирается попытка

Одна попытка на грейд, внутри секции по навыкам. Навыки — ядро специализации (`coreSkills`) плюс навыки из анкеты, для которых есть задания в банке.

| Специализация | Ядро                 |
| ------------- | -------------------- |
| Бэкенд        | http-api, postgresql |
| Фронтенд      | typescript, http-api |
| Данные        | postgresql           |
| Безопасность  | http-api, docker     |

В секции 4 задания. Сначала берётся по одному шаблону на тему, потом добор. Шаблон сам генерирует числа, имена и порядок вариантов от seed попытки. Форматы: один ответ, чтение кода, несколько ответов, число, порядок шагов. У каждого формата свой таймер: 60, 90, 90, 75 и 120 секунд.

Правила итога:

- секция засчитана от 70;
- попытка сдана, если средний балл от 70 и ни одна секция не ниже 50;
- от 90 профиль советует попробовать грейд выше;
- сданный другой грейд меняет подтверждённый, следующая смена через 90 дней. В паузе доступна пересдача на текущий: она обновляет балл и навыки.

## Сборка из вакансии

`planForNeed` переводит навыки `HiringNeed` в навыки банка через синонимы и добавляет ядро специализации. Навыки без заданий возвращаются в `uncovered`, по ним работодателю нечем проверить кандидата.

Запуск: `pnpm --filter @hh/assessment-engine vacancy-demo`.

```text
Бэкенд-разработчик в платёжный сервис — middle
  без заданий в банке: Kafka
  секция docker: layers; resources; images; volumes
  секция http-api: methods; caching; cors; pagination
  секция postgresql: joins; aggregates; transactions; nulls

Аналитик данных в маркетинг — senior
  без заданий в банке: Python
  секция postgresql: indexes; constraints; transactions; joins
```

Пробелы банка на примерах вакансий: Kafka, Python, OWASP.

## Защита от списывания

Сигналы копятся флагами. Чистота попытки — 100 минус штрафы. Ниже 40 попытка аннулируется и профиль не меняет.

| Сигнал                                   | Откуда                               | Штраф |
| ---------------------------------------- | ------------------------------------ | ----- |
| Уход на другую вкладку                   | `visibilitychange`                   | 15    |
| Переключение на другое окно              | `blur` дольше секунды                | 10    |
| Выход из полноэкранного режима           | `fullscreenchange`                   | 15    |
| Полноэкранный режим не включён           | отказ `requestFullscreen`            | 10    |
| Копирование, вырезание, контекстное меню | `copy`, `cut`, `contextmenu`         | 10    |
| Смена IP                                 | сервер, сравнение с прошлым запросом | 25    |
| Смена браузера                           | сервер, `User-Agent`                 | 40    |
| Ответ быстрее 3 секунд                   | сервер, `servedAt`                   | 10    |

Вопросы приходят по одному, назад вернуться нельзя. Таймер серверный: ответ позже срока с запасом 5 секунд засчитывается неверным. Новую попытку поверх открытой начать нельзя, иначе можно перебирать вопросы.

Ограничения:

- **Наложения не обнаруживаются.** Браузер не сообщает странице, что поверх окна нарисована другая программа. Виден только уход фокуса, и только если наложение его забирает. Прозрачные оверлеи и второй экран не видны.
- Телефон рядом, второй человек и виртуальная машина не видны.
- Клиентские флаги можно подавить, переписав JS. Серверные — IP, браузер, время ответа, таймер — нельзя.
- Встроенные браузеры и часть мобильных не дают полноэкранный режим. Это отдельный флаг с меньшим штрафом.

## Валидация на синтетических кандидатах

Запуск: `pnpm --filter @hh/assessment-engine validate`. Число заданий на секцию: `PER_SECTION=6`.

Модель кандидата: способность = грейд (1, 2, 3) + 0,35 + шум N(0; 0,3). Сложность задания = грейд + (difficulty − 2) / 2. Вероятность верного ответа — логистическая от разницы, плюс угадывание по формату: 25 % для одного ответа, 10 % для нескольких, 2 % для числа, 5 % для порядка. 400 кандидатов на грейд, навыки — ядро специализации и docker.

| Метрика                                 | 4 задания | 6       | 8       |
| --------------------------------------- | --------- | ------- | ------- |
| Измеренный грейд совпал с истинным      | 55,3 %    | 54,8 %  | 54,8 %  |
| Ошибка не больше соседнего грейда       | 98,8 %    | 98,9 %  | 99,6 %  |
| Пересдача на свой грейд с тем же итогом | 67,8 %    | 67,8 %  | 71,3 %  |
| Корреляция баллов при пересдаче         | 0,46      | 0,53    | 0,57    |
| Средняя дискриминативность шаблона      | 0,51      | 0,49    | 0,48    |
| Шаблонов с дискриминативностью ниже 0,2 | 9 из 77   | 7 из 77 | 8 из 77 |

Матрица при 4 заданиях, строки — истинный грейд, столбцы — нет / junior / middle / senior:

```text
junior: 71 / 307 / 22 / 0
middle:  2 / 186 / 207 / 5
senior:  0 / 13 / 237 / 150
```

Измеренный грейд — старший сданный, если идти снизу вверх. Дискриминативность — доля верных у верхних 27 % по баллу минус у нижних 27 %.

Вариативность: у двух попыток middle-бэкенда общих шаблонов 53,5 %, одинаковых формулировок с теми же вариантами 3,3 %.

Выводы:

- Тест почти не ошибается больше чем на грейд. Завышения редки, занижение на ступень частое. Порог 70 требует запаса над своим уровнем: кандидат «ровно middle» в этой модели набирает около 70 и проходит через раз.
- Длина секции слабо влияет на совпадение грейда, потому что расхождение даёт положение порога, а не шум. Пересдачу и корреляцию длина улучшает. Варианты: зона «на границе» 60–70 с бесплатной пересдачей, или 6 заданий на секцию, когда в каждой ячейке банка будет хотя бы 8 шаблонов.
- Слабые шаблоны — простые junior-вопросы (`ts-const-object`, `ts-optional-chaining`, `http-no-store`, `http-created`): их решают почти все. Их стоит усложнить или перенести в разминку.
- Модель проверяет правила оценки и согласованность с ручной разметкой difficulty, а не реальную валидность заданий. Для реальной калибровки нужны исходы по заданиям из живых попыток. Сейчас `assessment_attempts` хранит только секции. Следующий шаг — писать `templateId` и `correct` по каждому заданию и пересчитать difficulty и дискриминативность на них.
