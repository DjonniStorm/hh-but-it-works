# Тестирование: сборка, защита и валидация

Движок — `packages/assessment-engine`. API держит попытку в Redis и пишет итог в `assessment_attempts`. Ответы и верные варианты на клиент не уходят.

## Как собирается попытка

Одна попытка на грейд, внутри секции по навыкам. Навыки — ядро специализации (`coreSkills`) плюс навыки из анкеты, для которых есть задания в банке. Навык без своего банка добавляет в попытку секцию родственника: .NET — C#, Next.js — React, Node.js и NestJS — TypeScript, Django и FastAPI — Python, Spring — Java. Секция называется банком, и итог пишется только навыку банка: сданный C# появляется в анкете подтверждённым, .NET остаётся заявленным. Если в анкете есть и сам родственник, секция одна. Свой банк важнее: SQL, Linux, Redis, OWASP, Kafka и Pandas спрашиваются своими заданиями, SQL к PostgreSQL не сводится. Навык без банка и без родственника в попытку не входит и остаётся неподтверждённым. Лобби показывает секции попытки и отдельно такие навыки.

| Специализация | Ядро                 |
| ------------- | -------------------- |
| Бэкенд        | http-api, postgresql |
| Фронтенд      | typescript, http-api |
| Данные        | postgresql           |
| Безопасность  | http-api, docker     |

В секции 4 задания. Сначала берётся по одному шаблону на тему, потом добор. Шаблон сам генерирует числа, имена и порядок вариантов от seed попытки. Форматы: один ответ, чтение кода, несколько ответов, число, порядок шагов. У каждого формата свой таймер: 60, 90, 90, 75 и 120 секунд.

Правила итога:

- секция засчитана от 70;
- попытка сдана, если средний балл от 70 и ни одна секция не ниже 50;
- от 90 профиль советует попробовать грейд выше;
- сданный другой грейд меняет подтверждённый, следующая смена через 90 дней. В паузе доступна пересдача на текущий: она обновляет балл и навыки.

## Сборка из вакансии

`planForNeed` переводит навыки `HiringNeed` в навыки банка через синонимы и добавляет ядро специализации. Навыки без заданий возвращаются в `uncovered`, по ним работодателю нечем проверить кандидата.

Запуск: `pnpm --filter @hh/assessment-engine vacancy-demo`.

```text
Бэкенд-разработчик в платёжный сервис — middle
  без заданий в банке: нет
  секция docker: user; networking; pid; compose
  секция http-api: link; caching; get-body; cors
  секция kafka: delivery; delivery-order; group; order
  секция postgresql: check; aggregates; where-null; transactions

Фронтенд в личный кабинет — junior
  без заданий в банке: нет
  секция http-api: status; methods; versioning; redirect
  секция testing: double; setup; fixture; coverage
  секция typescript: spread; nullish; return-type; map-copy

Аналитик данных в маркетинг — senior
  без заданий в банке: нет
  секция postgresql: constraints; deadlock; repeatable-read; transactions
  секция python: metaclass; abc; multiprocessing; async-await
  секция sql: window; transaction; phantom; logical-order

Инженер AppSec — middle
  без заданий в банке: нет
  секция docker: user; networking; pid; compose
  секция http-api: link; caching; get-body; cors
  секция kubernetes: hpa; dns; statefulset; secret
  секция owasp: csrf; access-check; controls; idor
```

На этих вакансиях непокрытых навыков не осталось. У Kubernetes теперь свой банк, и в вакансии он идёт отдельной секцией, а не заданиями Docker. SQL спрашивается своим банком и не склеивается с PostgreSQL.

## Защита от списывания

Сигналы копятся флагами. Чистота попытки — 100 минус штрафы. Ниже 40 попытка аннулируется и профиль не меняет.

| Сигнал                                   | Откуда                               | Штраф |
| ---------------------------------------- | ------------------------------------ | ----- |
| Уход на другую вкладку                   | `visibilitychange`                   | 15    |
| Переключение на другое окно              | `blur` дольше секунды                | 10    |
| Выход из полноэкранного режима           | `fullscreenchange`                   | 15    |
| Полноэкранный режим не включён           | отказ `requestFullscreen`            | 10    |
| Копирование, вырезание, контекстное меню | `copy`, `cut`, `contextmenu`         | 10    |
| Смена IP                                 | сервер, сравнение с прошлым запросом | 25    |
| Смена браузера                           | сервер, `User-Agent`                 | 40    |
| Ответ быстрее 3 секунд                   | сервер, `servedAt`                   | 10    |

Вопросы приходят по одному, назад вернуться нельзя. Таймер серверный: ответ позже срока с запасом 5 секунд засчитывается неверным. Новую попытку поверх открытой начать нельзя, иначе можно перебирать вопросы.

Ограничения:

- **Наложения не обнаруживаются.** Браузер не сообщает странице, что поверх окна нарисована другая программа. Виден только уход фокуса, и только если наложение его забирает. Прозрачные оверлеи и второй экран не видны.
- Телефон рядом, второй человек и виртуальная машина не видны.
- Клиентские флаги можно подавить, переписав JS. Серверные — IP, браузер, время ответа, таймер — нельзя.
- Встроенные браузеры и часть мобильных не дают полноэкранный режим. Это отдельный флаг с меньшим штрафом.

## Валидация на синтетических кандидатах

Запуск: `pnpm --filter @hh/assessment-engine validate`. Число заданий на секцию: `PER_SECTION=6`.

Модель кандидата: способность = грейд (1, 2, 3) + 0,35 + шум N(0; 0,3). Сложность задания = грейд + (difficulty − 2) / 2. Вероятность верного ответа — логистическая от разницы, плюс угадывание по формату: 25 % для одного ответа, 10 % для нескольких, 2 % для числа, 5 % для порядка. 400 кандидатов на грейд, навыки — ядро специализации и docker. Новые банки в эти проценты не входят.

| Метрика                                 | 4 задания | 6         | 8         |
| --------------------------------------- | --------- | --------- | --------- |
| Измеренный грейд совпал с истинным      | 50,1 %    | 48,4 %    | 52,7 %    |
| Ошибка не больше соседнего грейда       | 98,2 %    | 99,1 %    | 99,4 %    |
| Пересдача на свой грейд с тем же итогом | 65,2 %    | 68,8 %    | 71,4 %    |
| Корреляция баллов при пересдаче         | 0,38      | 0,53      | 0,58      |
| Средняя дискриминативность шаблона      | 0,47      | 0,45      | 0,44      |
| Шаблонов с дискриминативностью ниже 0,2 | 21 из 177 | 29 из 177 | 23 из 177 |

Матрица при 4 заданиях, строки — истинный грейд, столбцы — нет / junior / middle / senior:

```text
junior: 72 / 307 / 20 / 1
middle:  0 / 206 / 190 / 4
senior:  0 / 21 / 275 / 104
```

Измеренный грейд — старший сданный, если идти снизу вверх. Дискриминативность — доля верных у верхних 27 % по баллу минус у нижних 27 %.

Вариативность: у двух попыток middle-бэкенда общих шаблонов 25,2 %, одинаковых формулировок с теми же вариантами 1,2 %.

В новых банках короче всех ячейка Kafka на junior: 6 шаблонов. Redis на junior и Kafka на senior — 7, senior у SQL, Linux, Redis, OWASP и Pandas — по 8. Секция берёт 4, так что попытка собирается. У Kubernetes, Git, System Design и Алгоритмов в каждой ячейке от 10 шаблонов.

Выводы:

- Тест почти не ошибается больше чем на грейд: 98,2 % при 4 заданиях. Завышение редкое (один junior из 400 измерен как senior). Занижение частое: из 400 senior своими признаны 104, ещё 275 остаются middle.
- Длина секции слабо двигает совпадение грейда: 50,1 %, 48,4 % и 52,7 %. Пересдачу и корреляцию длина улучшает: 65,2 % и 0,38 при 4 заданиях, 71,4 % и 0,58 при 8.
- Слабые шаблоны на 4 заданиях — простые junior-вопросы (`ts-spread`, `ts-optional-chaining`, `ts-boolean`, `ts-typeof`): их решают почти все. Их стоит усложнить или перенести в разминку.
- Модель проверяет правила оценки и согласованность с ручной разметкой difficulty, а не реальную валидность заданий. Для реальной калибровки нужны исходы по заданиям из живых попыток. Сейчас `assessment_attempts` хранит только секции. Следующий шаг — писать `templateId` и `correct` по каждому заданию и пересчитать difficulty и дискриминативность на них.
