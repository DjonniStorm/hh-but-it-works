# Пользовательский интерфейс

## Выбор подхода

При выборе решения для интерфейса рассматривались два подхода.

### SPA (Single Page Application)

Единый монолитный фронтенд. Позволяет быстро получить результат и опереться на огромное количество готовых решений от сообщества.

Главный минус - негативное влияние на SEO. Мы смягчили его с помощью библиотеки @unhead.

Решение масштабируется: достаточно добавлять новые компоненты и переиспользуемые схемы в контракты и начинать работу. Компоненты подгружают только то, что им нужно используя ленивую загрузку (lazy loading).

### Микрофронтенды

Приложение разбивается на домены, которые объединяются через Module Federation. Подходы с iframe, web components и подобные не рассматривались.

Для MVP у этого подхода существенные недостатки:

- рост сложности разработки при сжатых сроках;
- деление фронтенда не имеет смысла при монолитном бэкенде.

## Текущее решение

Фронтенд представляет собой SPA на React, сборка выполняется через Vite. Мы не стали делать "фреймворк над React", поэтому основной стек простой:

- MobX - управление состоянием;
- Mantine - UI-библиотека;
- Zod - общий валидатор схем для всего проекта;
- Nuqs - разбор и хранение состояния в URL;
- TypeScript - выразительный и типизированный код.

В планах развития проекта мы перейдем на модульную структуру.

## API-контракты

Чтобы клиент и сервер не расходились по контрактам, API-клиент генерируется по спецификации OpenAPI.
